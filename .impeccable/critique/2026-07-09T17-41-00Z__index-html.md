## Overall Impression

This is a genuinely well-crafted internal tool that's already absorbed two rounds of critique fixes — the validation, error-messaging, and toast subsystems are senior-level work. What's left is not "does this look like AI slop" (it doesn't) but two specific gaps: a real data-loss bug (inactivity logout bypasses the dirty-form guard) and a documentation/help vacuum (zero onboarding for acronym-heavy fiscal terminology). The single biggest opportunity is closing the inactivity-logout hole — it's the one finding here with genuine business risk (a vendedor losing a customer's captured data mid-conversation).

## What's Working

- **`_friendlyDbError` + collected validation + `_missingFieldsMsg`**: turns Postgres errors into plain Spanish, batches all missing fields into one toast, and correctly focuses the first bad field even across hidden multi-step panels via `_focusStepField`. Exactly the "confianza a través del detalle" the design brief asks for.
- **The toast component**: pauses auto-dismiss on `mouseenter`/`focusin`, resumes on leave, supports an action button, transitions rather than keyframes so an interrupted animation resumes smoothly. Unusually careful motion craftsmanship for a single-file app.
- **The document-lifecycle model**: `markPrinted` hides stale documents until the client record is re-saved, preventing a vendedor from handing over an out-of-date contract — solves a real business problem with a self-explanatory UI mechanism, no instructional copy needed.

## Priority Issues

**[P1] Inactivity auto-logout silently discards unsaved form data, bypassing the existing dirty-form guard**
- **Why it matters**: `resetInactivityTimer()` calls `doLogout()` directly after 5 idle minutes, without checking `_clientFormDirty` and without going through the `navigate()`/`beforeunload` guards that were built specifically to prevent this. A vendedor who steps away mid-intake (a customer test-drive, a manager check-in) for 5+ minutes returns to a blank login screen having lost captured RFC/CURP/domicilio data. This is the single scenario the dirty-form guard work was meant to prevent, left open on one path.
- **Fix**: Show a "¿Sigues ahí?" warning modal around minute 4 with a button that calls `resetInactivityTimer()`, and/or route the timeout through the same dirty-check confirmation path `navigate()` already uses.
- **Suggested command**: `/impeccable harden`

**[P1] Currency/phone/postal-code inputs don't set `inputmode`, forcing a full keyboard on tablet/phone**
- **Why it matters**: `f-precio`, `f-fsos`, `f-descuento`, `f-tel`, `f-tel-casa`, `f-tel-ofic`, `f-cp` are `type="text"` with no `inputmode` hint. On the sales-floor tablet scenario DESIGN.md explicitly calls out ("táctil primero... uso frecuente en tablet/celular en el piso de venta"), a vendedor typing a price or CP gets the full QWERTY keyboard instead of a numeric pad — a direct, easily-fixed violation of the project's own stated principle.
- **Fix**: add `inputmode="decimal"` to currency fields, `inputmode="numeric"` to CP, `inputmode="tel"` to phone fields.
- **Suggested command**: `/impeccable polish`

**[P2] Three new mismatched `<label for=>` associations (same bug class fixed once before)**
- **Why it matters**: Lines 3387, 3441, 3560 each have a `<label>` whose visible text describes one field but whose `for=` attribute points to a different field's id — likely from copy-pasting a label block into a new section without updating `for=`. Screen-reader users get a mislabeled control; this is the exact bug pattern manually patched earlier in this project's history.
- **Fix**: correct each `for=` to point at its own field's actual id (each affected id already has a second, correctly-labeled instance elsewhere to copy from).
- **Suggested command**: `/impeccable harden`

**[P2] `.tipo-fisica` badge color contradicts the documented single-accent design system**
- **Why it matters**: DESIGN.md states "Un solo acento de marca (azul BMW). Sin morado, sin gradientes," but `.tipo-fisica` uses purple (`#a78bfa`/`#6d28d9`) while `.tipo-moral` correctly stays blue. Either the badge or the doc is wrong, and nobody's reconciled it across three rounds of critique.
- **Fix**: bring `.tipo-fisica` into a blue/gray tonal variant, or explicitly amend DESIGN.md to document a second semantic hue for PF/PM distinction.
- **Suggested command**: `/impeccable harden`

**[P2] No sortable table columns and no Activity Log filters (power-user gap)**
- **Why it matters**: `clients-table` headers across dashboard/Mis Clientes/Todos Clientes are static text with no click-to-sort, and `renderActivityLog` has no filter by vendedor/action/date — just chronological scroll + "Cargar más." A gerente auditing daily activity or scanning clients by newest-first has no in-page way to do it.
- **Fix**: add click-to-sort on table headers (fecha, vendedor, nombre) and a simple filter row on Activity Log.
- **Suggested command**: `/impeccable optimize`

**[P3] Cliente step still exceeds the working-memory bar the rest of the form now respects**
- **Why it matters**: The Vehículo step was explicitly split into two labeled sub-sections in the prior round, but Step 1 "Cliente" — the largest step by field count (~30 fields across 3 unbroken `.form-card`s) — never got the same treatment, leaving the biggest cognitive-load violation in the form unaddressed while a smaller one was fixed.
- **Fix**: apply the same `.form-subsection-title` pattern already established for Vehículo (Datos Personales / Domicilio / Contacto e Identificación).
- **Suggested command**: `/impeccable layout`

## Persona Red Flags

**Casey (mobile/tablet, sales floor, one-handed, mid-conversation)**: Currency/phone/CP fields force the full keyboard instead of a numeric pad — every price and phone number typed on the floor costs extra taps. The Cliente step becomes a very long single-column scroll on narrow viewports with no jump-to-section control. The 5-minute inactivity logout is worst for this persona specifically, since floor conversations naturally have idle gaps (test-drives, financing check-ins) that easily exceed 5 minutes.

**Alex (power user — gerente/administrador triaging many clients daily)**: No column sorting anywhere in `clients-table`. `renderActivityLog` has no filter by vendedor/action/date, making "what did vendedor X do this week" impractical without leaving the page. Keyboard shortcuts cover search and new-client but nothing for jumping between nav sections.

**Sam (accessibility-conscious)**: `.form-control:focus{outline:none;border-color:var(--blue)}` removes the native focus outline and replaces it with only a 1px border-color shift — a weak focus signal for a low-vision user tabbing through a 30-field form, especially in bright ambient shop-floor light. The `.tipo-fisica` purple-on-navy combination (`#a78bfa` on `#1e1a3f`) is borderline for AA contrast at 11px badge text size.

## Minor Observations

- `renderClientDetail`/`df()` interpolate client-entered strings (e.g. `c.telefono`, address fields) without the `esc()` helper the export functions already use elsewhere in the file — worth a follow-up XSS-hardening pass since this is user-writable data rendered live.
- `CURP_REGEX` is defined with full state-code/consonant validation but `validateCURP()` only checks `length !== 18` — the "CURP válido" checkmark is weaker than the unused regex suggests it could be.
- `.role-pill` is uppercase via CSS; `.badge-tipo` (tipo-fisica/moral) is not — a small typographic inconsistency between two visually similar pill components.
- Nav items already have `title="${label}"` (added in the prior round), but acronym-heavy form labels (CFDI, BSI Plus, Fuente de Contacto options) don't reuse that same established tooltip pattern.
